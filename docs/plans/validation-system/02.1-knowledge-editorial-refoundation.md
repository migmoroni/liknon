# Phase 2.1: Knowledge Editorial Refoundation

## 1. Objective

Establish one standards-informed editorial architecture for the shared
validation knowledge delivered by `workspace-validator`.

This phase gives every substantive guide a predictable reading purpose,
category-specific structure, bounded depth, version policy, and maintenance
contract. It separates three concerns that must remain distinct:

1. the **editorial family**, which states why a reader opens a document;
2. the **editorial profile**, which defines the concrete structure of that kind
   of guide;
3. the **applicability facets**, which identify the languages, tools,
   technologies, frameworks, evidence dimensions, and workspace facts to which
   the guide may apply.

The resulting corpus remains concise and progressively disclosed. It directs a
reader toward sound validation decisions and authoritative depth without
becoming an offline encyclopedia or a version-specific manual for one
workspace.

The phase also refounds the existing content under the editorial profiles. It
does not merely move files. Every guide is reviewed for purpose, structure,
scope, version neutrality, terminology, duplication, source use, and
cross-document routing.

## 2. Position In The Validation System

Phase 2 provides the canonical knowledge tree, source register, embedded asset
pipeline, read-only knowledge CLI, routing fixtures, and release verification.
This phase preserves those capabilities while making the authored corpus
editorially coherent.

Phase 2.1 runs after Phase 2 and before Phase 3. Phase 3 may rely on shared
knowledge only after this phase is complete, because AI-Tool routing must not
amplify inconsistent structure, overly narrow version claims, or mixed
documentation purposes.

The phase does not add AI authority, flow activation, policy, persistence, or
validation execution behavior. It changes no `config.json` or report contract.

## 3. Authoritative Editorial Bases

The local editorial system is a deliberate profile over established technical
documentation standards, methodologies, and style guides. Each source retains
its real authority level; the project must not call a methodology or corporate
style guide a formal standard.

| Basis | Authority type | Adopted scope |
| --- | --- | --- |
| [ISO/IEC/IEEE 26514:2022](https://standards.ieee.org/ieee/26514/11031/) | Formal international standard | Audience analysis, information quality, consistency, lifecycle, and maintainability of user information |
| [OASIS DITA 1.3 plus Errata 02](https://docs.oasis-open.org/dita/dita/v1.3/errata02/os/complete/part0-overview/dita-v1.3-errata02-os-part0-overview-complete.html) | Formal OASIS standard | Topic orientation and the `concept`, `task`, `reference`, and `troubleshooting` information types |
| [Diataxis](https://diataxis.fr/) | Documentation methodology | Separation of explanation, how-to, reference, and tutorial purposes |
| [Google Developer Documentation Style Guide](https://developers.google.com/style) | Public technical-writing style guide | Direct language, active voice, reader-oriented instructions, terminology, headings, and code presentation |
| [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/) | Public technical-writing style guide | Clarity, concision, inclusive language, scannability, and consistent technical terminology |
| [RFC 7322](https://www.rfc-editor.org/rfc/rfc7322.html) | RFC editorial standard | Structure and precision for documents that summarize or define normative technical material |
| [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.html) | Internet Best Current Practice | Meaning of uppercase normative keywords when, and only when, a local normative contract intentionally uses them |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | W3C Recommendation | Accessible structure, link meaning, readable language, and non-visual dependence in rendered documentation |

Use OASIS DITA 1.3 plus Errata 02 as the stable DITA baseline. Do not make a
draft or beta DITA publication normative for this phase.

The local profiles adopt only the aspects declared below. They do not claim
full conformance to ISO/IEC/IEEE 26514, DITA, Diataxis, an RFC, or either style
guide. `docs/validation/authoring/editorial-bases.md` records each basis, its
authority type, exact edition or review scope, adopted aspects, and explicit
non-goals.

## 4. Scope And Invariants

### 4.1 Included Work

This phase includes:

- the information architecture below `docs/validation/knowledge/`;
- global writing and maintenance rules;
- one editorial profile for every catalog `kind`;
- one navigation profile for category and family indexes;
- version and source-scope rules;
- the catalog path contract and semantic validation;
- Markdown parsing and editorial conformance validation;
- refoundation of every current substantive guide and index;
- source-register corrections required by the refounded content;
- routing fixtures, forward trials, package contents, and documentation affected
  by the new paths or content scopes;
- deterministic tests and negative fixtures for the editorial contract.

### 4.2 Excluded Work

This phase does not:

- add tutorials without a demonstrated tutorial use case;
- attempt exhaustive coverage of a language, tool, framework, technology, or
  standard;
- copy upstream manuals into the crate;
- prescribe one universal validation stack;
- add AI-Tool or AI-Engineering instructions to shared knowledge;
- make network access part of normal knowledge retrieval or release validation;
- change validation planning, process execution, reports, policy, or
  persistence;
- create compatibility paths, aliases, redirects, duplicated trees, or
  transitional readers for replaced knowledge paths.

### 4.3 Preserved Invariants

- `docs/validation/knowledge/` remains the only authored shared-knowledge tree.
- `docs/validation/authoring/` contains maintainer guidance and is not itself
  shared validation knowledge.
- The installed CLI continues to retrieve knowledge by stable document ID.
- Existing document IDs remain stable when the document keeps the same semantic
  purpose; physical paths are not public selectors.
- `knowledge show` continues to return the exact canonical Markdown bytes.
- The embedded knowledge tree remains read-only, offline, deterministic, and
  independent from workspace initialization.
- The distributed skill contains no copied knowledge or authoring tree.
- `catalog.json` remains the compact routing contract.
- `sources.json` remains the canonical source register for substantive
  knowledge claims.
- All current paths and consumers are updated atomically to the target model.
- No migration, fallback, deprecated path, or parallel editorial model is
  created.

## 5. Information Architecture

### 5.1 Three Editorial Families

The corpus uses the three editorial families that have demonstrated use:

| Family | Reader intent | DITA basis | Diataxis basis |
| --- | --- | --- | --- |
| `explanation` | Understand a concept, risk, pattern, or validation context | `concept`, with bounded use of `troubleshooting` for concern-specific reasoning | Explanation |
| `how-to` | Accomplish a bounded validation goal in an adaptable sequence | `task` | How-to guide |
| `reference` | Look up precise behavior, terminology, commands, contracts, or external normative scope | `reference` | Reference |

Do not create a `tutorial` family in this phase. A tutorial teaches through a
progressive learning experience and requires a concrete learning journey,
prerequisites, exercises, and verified outcome. No current document has that
purpose.

### 5.2 Concrete Editorial Profiles

The existing catalog `kind` values become explicit editorial profiles. They are
not treated as equivalent directory labels or generic subject tags.

| Catalog `kind` | Editorial family | Canonical path prefix |
| --- | --- | --- |
| `foundation` | `explanation` | `explanations/foundations/` |
| `pattern` | `explanation` | `explanations/patterns/` |
| `concern` | `explanation` | `explanations/concerns/` |
| `language` | `explanation` | `explanations/languages/` |
| `technology` | `explanation` | `explanations/technologies/` |
| `framework` | `explanation` | `explanations/frameworks/` |
| `recipe` | `how-to` | `how-to/recipes/` |
| `tool` | `reference` | `reference/tools/` |
| `standard` | `reference` | `reference/standards/` |

Applicability tags remain the place for subjects and workspace facts. For
example, a Rust release recipe remains `kind: recipe`; `rust`, `cargo`, `cli`,
and `release` are applicability facets. A guide about Cargo remains
`kind: tool`; Rust is an applicability facet. Do not add duplicate documents
solely to place one subject under multiple directories.

## 6. Authoring Contract

### 6.1 Maintainer Documentation

Create `docs/validation/authoring/` outside the embedded knowledge root.

`README.md` explains the authoring workflow:

1. identify the reader question and editorial profile;
2. confirm applicability and authoritative sources;
3. author or revise the guide under the matching canonical path;
4. update catalog metadata and source records;
5. run the knowledge release check;
6. review the rendered document and routing behavior.

`editorial-standard.md` defines the global rules in this plan.

`editorial-bases.md` records every external basis from Section 3 with:

- authority type;
- exact edition, publication, or review scope;
- official URI;
- adopted aspects;
- aspects not claimed or adopted;
- applicability to local profiles.

Each profile file documents its purpose, bases, required structure, optional
structure, depth boundary, version treatment, examples, and review checklist.
It cites the relevant editorial bases explicitly rather than relying on a
generic statement elsewhere.

### 6.2 Machine-Readable Profile Contract

Create `docs/validation/authoring/editorial-profiles.json` and
`schemas/knowledge-editorial-profiles.schema.json`.

The profile registry contains:

- exact schema version;
- the three supported editorial families;
- one entry for every catalog `kind`;
- the family and canonical path prefix for each kind;
- the corresponding human profile document;
- the ordered H2 section contract;
- whether each section is required or optional;
- the editorial-basis IDs adopted by that profile.

Represent section order as one ordered array. A required section must appear;
an optional section may be omitted; every present section follows registry
order. Do not maintain a second heading map in Rust tests or release code.

The JSON registry is the machine-readable source of truth for profile mapping
and section order. The profile Markdown explains intent and use. Release checks
verify that every JSON profile has one Markdown profile and that each Markdown
profile names the same family, kind, and editorial bases.

### 6.3 Global Writing Rules

Every substantive guide:

- uses English, present tense, active voice, and direct reader-oriented prose;
- has one H1 title and one primary reader question;
- follows the H2 sequence declared by its editorial profile;
- uses H3 and deeper headings only within the meaning of their parent section;
- never skips heading levels;
- begins with purpose and applicability before commands or recommendations;
- distinguishes observations, evidence, inference, recommendation, and
  normative source requirements;
- explains what the proposed evidence can and cannot establish;
- states material mutation, cost, privilege, network, and external-service
  effects;
- keeps recommendations proportional to consequence and uncertainty;
- places citations adjacent to the supported claim;
- links to related local guides instead of repeating their substantive content;
- uses descriptive link text rather than raw URLs or vague text such as
  "here";
- describes code blocks before presenting them and identifies the language;
- labels placeholders and commands that require adaptation;
- never presents an example as universal project policy;
- reports missing coverage instead of inventing unsupported guidance.

Use title case consistently for H1 and H2 headings because the current public
documentation uses that convention. Code identifiers retain their native case.

### 6.4 Depth And Cognitive Load

Do not impose arbitrary word counts. Conformance is based on the function of
each section.

- A foundation explains the minimum conceptual model needed for a decision.
- A pattern explains one reusable solution and its consequences.
- A concern bounds one cross-cutting risk and the evidence needed to address it.
- A language, technology, or framework guide explains validation-specific
  failure surfaces, not the ecosystem generally.
- A tool reference documents only behavior relevant to validation planning and
  evidence interpretation.
- A standard reference preserves native terminology and points to the
  authoritative publication instead of reproducing it.
- A recipe is complete enough to adapt and execute, but remains one bounded
  composition rather than universal policy.

When a section has no meaningful content for a profile, the profile marks it
optional. Authors do not add filler merely to satisfy visual symmetry.

## 7. Editorial Profiles

### 7.1 Foundation

**Basis:** ISO/IEC/IEEE 26514 audience and information-quality principles,
DITA `concept`, Diataxis explanation, and the shared Google/Microsoft clarity
rules.

**Required H2 sequence:**

1. `Question`
2. `Applicability And Boundaries`
3. `Conceptual Model`
4. `Decision Guidance`
5. `Evidence And Limitations`
6. `Related Knowledge`

A foundation establishes vocabulary and reasoning used by several other
documents. It does not become a tool guide, procedural recipe, or exhaustive
theory chapter.

### 7.2 Pattern

**Basis:** DITA `concept`, Diataxis explanation, ISO/IEC/IEEE 26514 consistency,
and a local software-pattern profile that makes context and consequences
explicit.

**Required H2 sequence:**

1. `Problem And Context`
2. `Forces`
3. `Pattern`
4. `Consequences And Tradeoffs`
5. `Example`
6. `Failure Modes`
7. `Related Knowledge`

A pattern presents one reusable evidence-design solution. It must state when
the solution fails or becomes disproportionate. The local context/forces form
is a project profile; do not claim that DITA or Diataxis defines software
patterns.

### 7.3 Concern

**Basis:** DITA `concept` with bounded `troubleshooting` structure,
Diataxis explanation, and ISO/IEC/IEEE 26514 consequence-oriented user needs.

**Required H2 sequence:**

1. `Risk And Applicability`
2. `Consequences`
3. `Required Evidence`
4. `Limitations`
5. `Cost Mutation And External Services`
6. `Response And Next Step`

A concern addresses one cross-cutting risk. It does not prescribe a fixed tool
stack. It connects consequences to evidence and names residual uncertainty.

### 7.4 Language

**Basis:** DITA `concept`, Diataxis explanation, and Google/Microsoft guidance
for terminology and scannable technical comparisons.

**Required H2 sequence:**

1. `Scope`
2. `Failure Modes`
3. `Validation Layers`
4. `Evidence And Limitations`
5. `Version Scope`
6. `Related Tools And Recipes`
7. `Next Step`

A language guide distinguishes language semantics from runtime, package
manager, compiler, framework, and build-tool behavior. It covers maintained
major language or edition lines only when that distinction changes validation
decisions.

### 7.5 Technology

**Basis:** DITA `concept`, Diataxis explanation, and the shared
Google/Microsoft style rules.

**Required H2 sequence:**

1. `Role And Scope`
2. `Failure Modes`
3. `Validation Surfaces`
4. `Evidence And Limitations`
5. `Version Scope`
6. `Related Knowledge`
7. `Next Step`

A technology guide covers a runtime, protocol, platform, storage system, or
other technical environment that changes validation behavior. It does not
duplicate language or tool reference material.

### 7.6 Framework

**Basis:** DITA `concept`, Diataxis explanation, and the shared
Google/Microsoft style rules.

**Required H2 sequence:**

1. `Role And Scope`
2. `Framework-Specific Failure Modes`
3. `Validation Layers`
4. `Evidence And Limitations`
5. `Version Scope`
6. `Related Tools And Recipes`
7. `Next Step`

A framework guide explains validation behavior introduced by the framework. It
does not become a framework tutorial or repeat the underlying language guide.

### 7.7 Recipe

**Basis:** DITA `task`, Diataxis how-to, ISO/IEC/IEEE 26514 task orientation,
and Google/Microsoft procedural-writing guidance.

**Required H2 sequence:**

1. `Goal`
2. `Applicability And Preconditions`
3. `Risks And Invariants`
4. `Inputs And Workspace Assumptions`
5. `Procedure`
6. `Complete Configuration Example`
7. `Expected Evidence`
8. `Failure Interpretation`
9. `Limitations And Residual Risk`

A recipe provides one adaptable end-to-end validation composition. Commands and
configuration are internally consistent and non-publishing by default. The
recipe does not depend on this repository's private layout or claim to be a
minimum, recommended, or universal gate for every consumer.

### 7.8 Tool

**Basis:** DITA `reference`, Diataxis reference, and Google/Microsoft command and
technical-reference style guidance.

**Required H2 sequence:**

1. `Purpose And Scope`
2. `Version Lines And Sources`
3. `Command Model`
4. `Inputs Outputs And Exit Status`
5. `Mutation Cost And External Services`
6. `Evidence Produced`
7. `Blind Spots`
8. `Related Knowledge`

A tool guide explains how the tool contributes evidence. It is not a command
manual. Include only representative command forms needed to understand
selection, effects, output, and limits.

### 7.9 Standard

**Basis:** DITA `reference`, Diataxis reference, the source publication's own
native structure, RFC 7322 where normative technical prose is summarized, and
RFC 8174 only where uppercase normative keywords are intentionally used.

**Required H2 sequence:**

1. `Authority Scope And Version`
2. `Native Terminology And Conformance`
3. `Applicability`
4. `Evidence And Limitations`
5. `Misuse To Avoid`
6. `Sources And Next Step`

A standard guide preserves the authority, version, levels, and conformance
meaning of the external publication. It never invents local conformance levels
or presents an automated check as proof of complete conformance.

### 7.10 Navigation

**Basis:** DITA map/navigation principles, ISO/IEC/IEEE 26514 findability, and
Diataxis separation by reader purpose.

A family or category `README.md` contains:

1. one H1 naming the family or category;
2. a concise statement of reader intent and boundary;
3. an ordered list of current guides with descriptive summaries;
4. routing guidance to adjacent families or categories when useful.

Indexes contain no independent substantive recommendation. A recommendation
belongs in one cataloged guide and the index links to it.

## 8. Version And Source Policy

### 8.1 Separate Applicability From Provenance

The prose scope of a guide and the exact revision used to review a claim are
different data.

- Guide prose describes stable concepts or relevant major version lines.
- `sources.json` records exact editions, tags, commits, or dated living
  documentation reviews for traceability.
- An exact source snapshot does not narrow the guide to that patch release.
- A patch version appears in substantive prose only when behavior materially
  changes at that patch and the guide explains the distinction.

Do not use one development workstation's installed patch version as the scope
of public knowledge.

### 8.2 Tool Version Lines

Every tool guide includes `Version Lines And Sources`.

- List the maintained major lines that have distinct official documentation or
  behavior relevant to the guide.
- Link each listed major line to its authoritative documentation or release
  family.
- State shared behavior once.
- Use a compact comparison only when behavior differs.
- Avoid `latest`, `current`, and other moving labels without a date and an
  explicit living-documentation status.
- Tell readers to confirm the version active in their workspace before applying
  version-sensitive commands.

For pnpm, represent major lines 11 and 12 separately in the source register and
tool guide. Do not make `11.22.0` the identity or reader scope of the guide. An
exact reviewed patch, tag, or commit may remain source-provenance metadata.

Apply the same review to Node.js, TypeScript, Vitest, Rust/Cargo, Git,
workspace-validator, and future tools. Preserve exact versions for standards or
language editions whose identity is inherently versioned, such as WCAG 2.2 or
ECMAScript 2025.

### 8.3 Recipes And Examples

- Recipes identify required capabilities and major-line assumptions rather
  than one incidental patch version.
- Complete configuration examples remain schema-valid and executable after
  replacing declared placeholders.
- A repository-specific command is included only when the recipe explicitly
  declares that repository shape as an example.
- Shared recipes do not validate workspace-validator's own private source tree,
  skills, or embedded assets unless the recipe's public purpose is explicitly a
  workspace-validator contributor gate. General Rust CLI recipes remain general
  Rust CLI recipes.
- Tool version differences link to the tool reference rather than being copied
  into every recipe.

### 8.4 Source Register

Refactor source records as needed so they distinguish:

- the source's applicable standard edition or major product line;
- the exact revision or living snapshot reviewed for provenance;
- the authoritative primary URI;
- precise locations supporting local claims;
- publication status and review date.

Use one source ID per materially distinct major documentation line when a tool
maintains parallel versioned documentation, for example `pnpm.cli-11` and
`pnpm.cli-12`. Do not encode patch versions in stable source IDs.

Regenerate `SOURCES.md` deterministically after the source contract and records
are updated.

## 9. Markdown And Editorial Validation

### 9.1 Structured Markdown Parsing

Replace ad hoc heading, link, citation, and fenced-example discovery in the
knowledge release path with one parsed CommonMark event or AST representation.
Use a maintained Rust Markdown parser as a development/release dependency,
subject to explicit human authorization and MSRV `1.87.0` verification before
it is added.

The parser is not a runtime dependency of validation execution or knowledge
retrieval. It is used only by release tooling and tests.

One parsed document supports:

- H1 and H2 structure validation;
- heading-level continuity;
- exact section ordering by editorial profile;
- internal and external link extraction;
- source citation extraction;
- fenced code-block language and content extraction;
- exact recipe JSON extraction without mistaking prose or nested fences;
- title and section diagnostics with source paths and line numbers.

Do not retain parallel string scanners after the parsed implementation covers
their contracts.

### 9.2 Semantic Rules

The release check rejects:

- a catalog kind without exactly one editorial profile;
- a profile mapped to an unsupported family;
- a document outside the path prefix declared for its kind;
- missing, duplicate, unknown, or out-of-order required H2 sections;
- heading-level skips;
- multiple H1 headings;
- an H1 that does not match the document title contract;
- category or family indexes with missing or unlisted guides;
- substantive uncataloged Markdown below the knowledge families;
- a cataloged document without an embedded asset;
- unresolved local links, citations, relationships, or source IDs;
- recipe JSON that is missing, duplicated, malformed, schema-invalid, or
  semantically invalid;
- version-specific reader scope that contradicts catalog metadata or the tool's
  declared major-line section;
- authoring profile JSON and profile Markdown that disagree.

Diagnostics identify the document ID, canonical path, profile, violated
section, and expected structure.

### 9.3 Human Review Boundary

Automation validates structure and resolvable contracts. Human review remains
responsible for:

- whether the selected profile matches reader intent;
- whether prose is concise and comprehensible;
- whether evidence claims are technically correct;
- whether source locations actually support adjacent claims;
- whether depth is proportional;
- whether version distinctions are materially useful;
- whether examples are safe and realistic;
- whether two documents duplicate the same substantive guidance.

Add a bounded review checklist for these questions to every profile and to the
shared knowledge review rubric.

## 10. Corpus Refoundation

### 10.1 Inventory And Classification

Before moving files, produce a deterministic inventory of every substantive
guide and navigation asset containing:

- current stable ID where applicable;
- current kind;
- target family and path;
- primary reader question;
- applicability facets;
- source IDs;
- selected editorial profile;
- version-scope action;
- duplication or split/merge decision.

The inventory is an implementation aid and test fixture, not a second runtime
catalog. Remove it after the canonical catalog and tests encode the completed
state unless it remains useful as a clearly named review artifact under
`docs/validation/authoring/`.

### 10.2 Structural Refoundation

Move every guide and index directly to the target layout. Update the catalog,
links, navigation arrays, fixtures, tests, docs, package assertions, and
embedding expectations in the same change.

Do not leave forwarding files at replaced paths.

### 10.3 Content Refoundation

Rewrite each current guide to its profile without changing technically correct
claims merely for stylistic variation.

For every document:

1. identify one primary reader question;
2. confirm the profile and applicability;
3. reorganize content into the required section sequence;
4. remove duplicated or out-of-scope material;
5. add missing evidence limits, effects, and next steps;
6. make version scope major-line or edition oriented;
7. verify every adjacent citation and source location;
8. repair related-document links;
9. review terminology and voice;
10. update catalog summary, questions, relations, status, and review date.

### 10.4 Initial Corpus-Specific Requirements

- Foundations use one vocabulary and link instead of redefining evidence,
  oracle, consequence, or residual risk independently.
- Patterns make forces and tradeoffs explicit.
- The reproducible-release concern remains ecosystem-neutral; Rust and
  JavaScript examples live in scoped guides or recipes.
- Language guides separate language semantics from runtime, compiler, package
  manager, framework, and build-tool behavior.
- Node.js remains a technology guide rather than a JavaScript language guide.
- Tool guides cover evidence behavior and operational effects, not complete CLI
  manuals.
- The pnpm tool guide covers major lines 11 and 12 without using one patch as
  its public identity.
- The workspace-validator tool guide describes the installed CLI version that
  carries the embedded guide and directs the reader to `--version`; it does not
  present one source commit as general applicability.
- WCAG preserves its native 2.2 identity, levels, and conformance meaning.
- Recipes are adaptable public examples and contain no hidden dependency on the
  workspace-validator repository unless explicitly scoped as contributor
  documentation outside shared knowledge.

## 11. Implementation Sequence

### Step 1: Protect The Accepted Baseline

- Run the complete Phase 2 release and test matrix.
- Record the canonical knowledge digest and current routing fixture results.
- Confirm the worktree changes that belong to the implementation before
  editing.

### Step 2: Establish Authoring Contracts

- Create `docs/validation/authoring/`.
- Author the editorial standard, bases, machine profile registry, and ten
  profile documents.
- Add and compile the profile JSON Schema.
- Add positive and negative profile fixtures.

### Step 3: Centralize Markdown Parsing

- Request authorization for the selected development-only Markdown parser.
- Verify its MSRV and supply-chain status.
- Build one internal parsed-document model for release tooling.
- Move heading, link, citation, and fenced-code extraction to that model.
- Remove covered string-scanning implementations.

### Step 4: Enforce Editorial Semantics

- Load and validate the profile registry once per release-check invocation.
- Map every catalog kind to exactly one profile.
- Enforce canonical path prefixes and heading contracts.
- Add precise diagnostics and negative tests.

### Step 5: Reorganize The Canonical Tree

- Create the three family trees and their category indexes.
- Move substantive guides to canonical paths.
- Update catalog paths, navigation, links, embedding inventory, and package
  assertions atomically.

## 12. Test Matrix

### 12.1 Profile Contract Tests

Cover:

- every supported kind and family;
- exact path-prefix mapping;
- missing and duplicate profile entries;
- unknown fields and enum values;
- missing and out-of-order required sections;
- optional section omission and correct placement;
- duplicate or unknown H2 sections;
- multiple H1 headings and heading-level skips;
- profile JSON/Markdown disagreement;
- navigation assets outside substantive catalog inventory.

### 12.2 Markdown Parser Tests

Cover:

- headings inside fenced code that must not affect structure;
- inline code and links containing heading markers;
- nested parentheses and fragments in links;
- source citations adjacent to punctuation;
- multiple fenced languages;
- one exact recipe JSON block;
- malformed and unclosed fences;
- line-number diagnostics;
- UTF-8 prose without unsafe paths.

### 12.3 Version And Source Tests

Cover:

- multiple supported major-line source IDs for one tool;
- exact standard editions that intentionally remain versioned;
- living documentation with an explicit review date;
- immutable provenance that does not narrow guide applicability;
- rejection of patch-only tool identity in titles and summaries unless an
  explicitly reviewed behavioral distinction requires it;
- stale generated `SOURCES.md`;
- unresolved source locations and unsupported adjacent claims in review
  fixtures.

### 12.4 Corpus And Routing Tests

Cover:

- every substantive Markdown guide exactly once in the catalog;
- every catalog guide under its profile path;
- every family and category index listing current children;
- exact embedded bytes after moves;
- stable document-ID lookup through the CLI;
- routing fixtures selecting profiles without cross-loading unrelated subjects;
- recipes remaining schema-valid and non-executing during release validation;
- empty-directory installed-package retrieval.

### 12.5 Negative Fixtures

Keep deterministic temporary or checked-in fixtures for each structural failure
class. Do not corrupt the canonical corpus to test rejection. Every negative
fixture must prove the same validator used by the release check rejects the
condition with a useful diagnostic.

## 14. Handoff To Phase 3

Phase 3 begins only after every acceptance criterion in this document is
complete.

AI-Tool consumes the refounded corpus through stable document IDs and
progressive CLI retrieval. It does not interpret physical directory names as
authority, copy authoring contracts into the skill, or treat an editorial
profile as executable validation policy.

Future corpus growth follows the same process: identify a demonstrated reader
question, choose one existing profile, add authoritative sources, write the
smallest sufficient guide, validate it mechanically, and review it editorially.
A new profile or tutorial family requires a separate explicit design decision.
