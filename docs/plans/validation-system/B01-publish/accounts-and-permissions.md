# B01 External Accounts, Permissions, And Publication Authority

[Back to the distribution plan](README.md)

## Purpose

This runbook stages the human-owned account, permission, and credential work for
Plan B01. It is not an additional implementation phase and it is not a checklist
that must be completed all at once. Each B01 phase links to the checkpoint that
must be complete before that phase can finish.

An existing account satisfies the account-creation item after its ownership,
recovery, and required permissions are verified. Do not create duplicate
accounts merely to satisfy this document.

## Publication Authority

The release authority is intentionally split:

- The human release owner controls registry and Cloudflare accounts, creates the
  signed release tag, reviews release evidence, and authorizes publication.
- GitHub Actions is the normal release executor. It builds, seals, packages,
  publishes, reads artifacts back, and records evidence from the exact retained
  candidates.
- The credential-free `release-approval` environment represents human approval.
  It contains no signing or publication credential.
- Each signing or destination job receives only its own GitHub environment,
  identity, and minimum permissions after approval.
- The maintainer workstation is not a second build or routine publication path.

The first crates.io and npm versions cannot use trusted publishing before their
package identities exist. Their bootstrap publication still runs in GitHub
Actions, using one destination-scoped credential placed temporarily in the
matching protected environment and revoked immediately afterward. This keeps
the published package tied to CI evidence instead of a local rebuild.

If a provider's current policy technically requires an interactive human upload,
the maintainer may download the exact retained candidate from the approved
workflow and upload that unchanged artifact. The exception must be recorded in
the release evidence. It never permits rebuilding, restaging, or editing a
package on the workstation.

## Canonical GitHub Identities

Use these exact identities unless the plan is deliberately amended before any
external trust relationship is created:

| Purpose | Canonical identity |
| --- | --- |
| Repository | `migmoroni/liknon` |
| Release workflow | `.github/workflows/release.yml` |
| Human approval | `release-approval` |
| Detached release signing | `sign-release` |
| Windows native signing | `sign-windows` |
| GitHub Release publication | `publish-github` |
| Cloudflare publication | `publish-cloudflare` |
| crates.io publication | `publish-crates-io` |
| npm publication | `publish-npm` |
| RubyGems publication | `publish-rubygems` |
| PyPI publication | `publish-pypi` |
| NuGet publication | `publish-nuget` |

Registry trusted-publisher policies must bind the exact repository, workflow
filename, and destination environment wherever the provider supports those
claims. Renaming any identity after binding it requires updating and retesting
every affected policy.

The release workflow declares permissions per job. Build, assembly, and
verification use `contents: read`. OIDC publication jobs additionally use
`id-token: write`. Only the isolated GitHub Release job receives
`contents: write`. No workflow receives broad write permission by default.

## Package Identity Inventory

The external account owner must understand the identity count before granting a
scope or trusted-publishing policy:

| Destination | Public identities |
| --- | --- |
| crates.io | One crate: `liknon` |
| npm | Root `liknon` plus seven `@liknon/<platform>` packages |
| RubyGems | One gem `liknon` with seven platform variants |
| PyPI | One project `liknon` with seven platform wheels |
| NuGet | Pointer `liknon` plus seven `liknon.<rid>` packages |
| Cloudflare | One production bucket and one project-controlled download domain |

Availability checks do not reserve a package name. Do not publish placeholder
packages merely to claim names. Each first accepted package must be a reviewed
Liknon release candidate.

## Credential Placement

| Identity or credential | Location | Lifetime |
| --- | --- | --- |
| GitHub OIDC identities | Generated by the destination job | Minutes; never stored |
| crates.io bootstrap token | `publish-crates-io` environment | First publication only; then revoke and remove |
| npm bootstrap credential | `publish-npm` environment | First publication only; then revoke and remove |
| R2 access key and secret | `publish-cloudflare` environment | Persistent but bucket-scoped and rotated |
| Detached-signing private key | `sign-release` environment | Persistent, separately backed up and rotated |
| Windows PFX and password | `sign-windows` environment | Persistent project identity, separately backed up |
| NuGet public username | `publish-nuget` environment variable | Non-secret configuration |
| Human Git tag signing key | Maintainer-controlled local or hardware key | Never copied to publication jobs |
| Account recovery codes | Offline maintainer storage | Never stored in GitHub or the repository |

Do not place destination credentials in repository-wide secrets when an isolated
environment can hold them. Never commit credentials, copy them into workflow
artifacts, or expose them to build and verification jobs.

### AP-0

**Release ownership inventory. Complete before Phase B01.0.**

- [ ] Record which GitHub, crates.io, npm, RubyGems, PyPI, NuGet, and Cloudflare
      accounts already exist.
- [ ] Choose the accountable individual or organization for each destination.
- [ ] Verify access to the contact email and enable strong multi-factor
      authentication on every existing account.
- [ ] Store recovery codes outside GitHub and outside the repository.
- [ ] Record intended package names and current availability without publishing
      placeholders.
- [ ] Record the existing Cloudflare account and domain owner.

No registry trusted publisher, API token, R2 upload credential, or signing secret
is required at this checkpoint.

### AP-1

**GitHub release identity. Complete before Phase B01.1.**

- [ ] Confirm `migmoroni/liknon` is the canonical public repository.
- [ ] Enable GitHub Actions and use `.github/workflows/release.yml` as the stable
      release-workflow identity.
- [ ] Create the named GitHub environments without publication credentials.
- [ ] Set the default `GITHUB_TOKEN` posture to read-only and grant writes only
      per job.
- [ ] Protect the release workflow and release tags through the repository's
      applicable rules.
- [ ] Enable immutable GitHub Releases.
- [ ] Configure and test the human-owned key used to create signed annotated
      release tags.

### AP-2

**Native signing readiness. Complete before Phase B01.2.**

- [ ] Create one persistent project-controlled self-signed Windows code-signing
      identity and record its public certificate fingerprint.
- [ ] Store its PFX and password only in `sign-windows` and in an independent
      offline recovery location.
- [ ] Select and test the RFC 3161 timestamp service used by Windows signing.
- [ ] Confirm that macOS uses ad hoc signing and therefore requires no Apple
      developer account or signing secret.
- [ ] Confirm GitHub-hosted Windows and macOS runners are available to the
      repository.

The Windows certificate is not imported into user trust stores and is not
shared with another environment.

### AP-3

**crates.io account readiness. Complete before Phase B01.3.**

- [ ] Sign in to crates.io through the intended GitHub owner and verify the
      account email.
- [ ] Confirm the intended owner can publish `liknon` and record any future
      GitHub team ownership.
- [ ] Recheck the crate name immediately before relying on it.
- [ ] Confirm the account can create a narrowly scoped bootstrap token later.

Do not create or store the bootstrap token yet. crates.io requires the first
crate version to exist before trusted publishing can be configured; token
creation belongs to AP-10.

### AP-4

**Cloudflare and release-signing foundation. Complete before Phase B01.4.**

- [ ] Confirm access to the existing Cloudflare account and domain.
- [ ] Activate R2 and any required billing profile.
- [ ] Ensure the DNS zone and R2 bucket are owned by the same Cloudflare account.
- [ ] Create the production bucket and attach the chosen download subdomain.
- [ ] Keep the public `r2.dev` endpoint disabled for production.
- [ ] Configure the immutable-prefix, cache, TLS, monitoring, and budget policy
      required by the public contract.
- [ ] Select the detached-signature mechanism and create its persistent signing
      identity.
- [ ] Store the private signing material only in `sign-release` and an
      independent offline recovery location; publish its trust root outside R2.

Do not create a broad Cloudflare administrator credential for the release job.
The bucket-scoped upload credential is created at AP-10.

### AP-5

**npm account and scope readiness. Complete before Phase B01.5.**

- [ ] Verify the publishing account, email, MFA, and recovery access.
- [ ] Create or confirm ownership of the `@liknon` organization or scope.
- [ ] Assign only the maintainers required to administer the root and platform
      packages.
- [ ] Recheck `liknon` and all seven platform package names.
- [ ] Record that platform packages publish before the root package.

Do not publish placeholders. npm trusted-publisher configuration requires an
existing package and currently must complete its first successful trusted
publish within a short validation window, so it is not created during this
checkpoint.

### AP-6

**RubyGems account readiness. Complete before Phase B01.6.**

- [ ] Verify the RubyGems account, email, MFA, and recovery access.
- [ ] Confirm the `liknon` gem name and accountable owner.
- [ ] Record `release.yml` and `publish-rubygems` as the intended trusted
      publisher identity.

RubyGems can create a new gem from a pending trusted publisher. Create that
pending binding at AP-10, close to publication, rather than now.

### AP-7

**PyPI account readiness. Complete before Phase B01.7.**

- [ ] Verify the PyPI account, email, 2FA, and recovery access.
- [ ] Confirm the `liknon` project name and accountable owner.
- [ ] Record `release.yml` and `publish-pypi` as the intended trusted publisher
      identity.

PyPI can create a project through a pending trusted publisher, but the pending
entry does not reserve the name. Create it at AP-10 immediately before the first
publication attempt.

### AP-8

**NuGet account readiness. Complete before Phase B01.8.**

- [ ] Verify the nuget.org account, Microsoft-account MFA, and recovery access.
- [ ] Choose and record individual or organization ownership.
- [ ] Confirm the pointer and seven RID package IDs.
- [ ] Define the narrow trusted-publishing scope that covers only `liknon` and
      the intended `liknon.<rid>` identities.
- [ ] Record `release.yml`, `publish-nuget`, and the public NuGet username.

Create the actual trusted-publishing policy at AP-10 after the workflow and
package inventory have passed end-to-end verification.

### AP-9

**Credential-free release-candidate verification. Complete before Phase B01.9.**

- [ ] Confirm release-candidate jobs can exchange private GitHub Actions
      artifacts without a destination credential.
- [ ] Confirm local registry fixtures and isolated package-manager homes require
      no public-registry write access.
- [ ] Prove build, assembly, and verification jobs cannot read any signing or
      publication environment.
- [ ] Review the account inventory and record any unresolved AP-10 action.

No public destination credential is introduced in this checkpoint.

### AP-10

**Just-in-time publication activation. Complete as Phase B01.10 begins.**

- [ ] Create the RubyGems pending trusted publisher for `release.yml` and
      `publish-rubygems`.
- [ ] Create the PyPI pending trusted publisher for `release.yml` and
      `publish-pypi`.
- [ ] Create the NuGet trusted-publishing policy for the exact repository,
      workflow, environment, owner, and package scope.
- [ ] Configure each OIDC publication job with only `contents: read` and
      `id-token: write`.
- [ ] Create one R2 Object Read & Write credential scoped only to the production
      bucket and store it in `publish-cloudflare`.
- [ ] Create the crates.io first-publication token, store it only in
      `publish-crates-io`, and record its revocation step.
- [ ] Create the safest currently supported npm bootstrap credential, preferably
      stage-only with interactive 2FA approval, store it only in `publish-npm`,
      and record its revocation step.
- [ ] Verify `sign-release` and `sign-windows` contain only their own signing
      identities.
- [ ] Create and push the signed annotated release tag only after every
      pre-publication check passes.
- [ ] Approve the credential-free `release-approval` gate after reviewing the
      retained candidate inventory and destination preflight.

GitHub Actions performs all normal uploads. It publishes dependency leaves first
and root or pointer packages last. The human authorizes and, where a registry
requires it, completes an interactive approval; the human does not rebuild or
restage packages locally.

### AP-11

**Post-publication closure. Complete during Phase B01.11.**

- [ ] Revoke crates.io and npm bootstrap credentials immediately and remove
      their GitHub environment secrets.
- [ ] Configure crates.io trusted publishing for future releases after the first
      crate exists.
- [ ] Confirm RubyGems and PyPI pending publishers became normal trusted
      publishers and NuGet's policy became fully active.
- [ ] Do not create npm trusted publishing until a subsequent release is ready
      to satisfy its current activation window; record that required next-release
      action explicitly.
- [ ] Verify every package and platform variant is owned by the intended account
      or organization.
- [ ] Verify the R2 credential remains bucket-scoped and schedule its rotation.
- [ ] Confirm no account recovery code, registry token, or signing private key
      entered logs or release evidence.
- [ ] Publish the stable pointer only after every public installation path passes.
